# Threat model

Policy: [DESIGN.md](DESIGN.md). Acceptance tests: [IMPLEMENTATION.md](IMPLEMENTATION.md#security-testing-acceptance-criteria).

Assets: passkey bindings, sessions/recovery secrets, pseudonym continuity, private verification receipts, restriction/appeal records, privileged grants, evidence history, and anonymous readers' privacy. Adversaries include account thieves, scripted signups, impersonators, abusive members, colluding staff, compromised providers, and infrastructure operators. Boundaries are browser/server, public/private projections, app/broker databases, provider callbacks, staff tools, logging/backups, and exported data.

| Threat                                                     | Proposed controls                                                                                                         | Residual risk / test                                                                        |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Phishing, forged credential, ceremony replay               | RP/origin validation, UV, bound challenge and atomic consumption                                                          | Compromised device/cloud passkey sync remains possible; negative protocol fixtures          |
| Session theft/fixation or CSRF                             | Hashed opaque tokens, rotation, secure cookie, origin/token protection, live revocation                                   | XSS can act as a user; CSP and output safety review needed                                  |
| Recovery takeover                                          | Second passkey preferred; single-use code, bound hold, restricted session, no provider/email override                     | Stolen code can cause temporary lockout; contest flow and rate limits required              |
| Handle impersonation                                       | Unique canonical handle, reserved staff terms, explicit role labels, no recycled handles                                  | ASCII lookalikes and off-platform impersonation persist; reports and human correction       |
| Mass account creation                                      | Signup quotas, short-lived ceremony limits, progressive newcomer write quotas, invite-only pilot                          | Passkeys do not prove one human; no perfect Sybil resistance promised                       |
| Ban evasion                                                | Live restrictions, credential reuse detection, narrow pairwise verification token only when available, human-linked cases | New passkeys/unverified accounts evade linkage; no mandatory L2 or global identity registry |
| NAT/VPN/shared-device false positive                       | Small temporary delays, accessible challenge alternatives, independent appeal                                             | Never ban solely for IP, VPN, credential counter, or inferred linkage                       |
| Leaking L2 status through profile/search/export/cache      | DTO allowlists, separate store, owner-only no-store routes, cross-account tests                                           | Public L3 role implies a role assessment; never disclose route or receipt                   |

## Proportionate abuse controls

Begin with an invitation pilot and configurable per-account/action quotas, not a device fingerprint or behavioral profile. Rate-limit ceremonies by rotating keyed network-prefix buckets and account/credential handles; prefer early rejection before costly cryptography. Raw IPs are processed transiently at the edge, not persisted in application logs. Quota thresholds require pilot measurement and approval; do not invent claims of detection accuracy.

Escalate from delays to temporary write restriction to human-reviewed suspension. Give a safe reason and an appeal route without exposing other users, internal signals, or private verification status. Restriction evaluation happens before grant checks; staff and L2 members have no immunity. Do not use cross-site tracking, advertising IDs, continuous biometrics, contact graphs, political profiling, or secret reputation scores. Ban-evasion candidates require corroborated human review; broker equality alone is not a ban decision.

Provider/internal email/support systems must not become a covert document intake channel. Verification appeals use structured codes and provider-hosted dispute processes; unsolicited sensitive payloads are rejected before persistence and never copied into tickets. Incident response must include accidental PII in logs/backups and compromised signing keys, not only credential theft.
